# Strava integration regression tests

Run `python3 ci/strava_tests.py` with Java 17 and Python. No Strava account, API registration, Android SDK, emulator, or personal recording is needed. Initial setup fetches three checksum-pinned test-only JARs from Maven Central. The actual tests direct every HTTP connection to a loopback server and reject unexpected production hosts/paths. They never use the default production connection factory, real credentials, or real Strava uploads. Runtime tests finish in a few seconds because the clock and polling delay are injected.

The Android `StravaApi` delegates protocol handling to the same `StravaClient` compiled by this suite. Only the Android URI adapter and Keystore-backed settings are outside this JVM harness. Tests use real `HttpURLConnection` serialization and disk-backed `RideStore` recordings generated by the existing synthetic ascent/FIT fixture: 20 m riding ascent, 100 m excluded lift ascent, 44 retained samples.

| Area | Automated evidence |
| --- | --- |
| OAuth | Authorization endpoint/fields, fresh persisted state, callback address, rejected userinfo/ports/fragments/duplicate parameters, missing or incorrect state, denial, missing/blank codes, required read/write scopes, encoded token exchange, one-use callback state, failed exchanges, invalid token responses, changed client configuration |
| Tokens | Valid-token reuse, exact 120-second refresh boundary, expiration, rotated refresh-token persistence/use, rejection of incomplete/expired responses, preservation of the last stored token set on refresh failure |
| FIT submission | Multipart fields and CRLF/boundary framing, bearer authentication, stable external ID, binary equality with the corrected FIT, completion/valid-ascent gates, durable status before any file bytes are sent |
| Processing | Pending responses, bounded 25-poll window with two-second gaps, immediate completion, initial and later processing errors, large upload/activity IDs, app-restart recovery using persisted IDs, interrupted polling |
| Elevation | Matching, exact ±1 m tolerance, mismatches in both directions, actual/expected values, invalid activity responses, failed rechecks clearing stale verified state, no FIT or sample rewriting |
| Failure/recovery | HTTP errors including authentication/rate limiting/server errors, redirects disabled, malformed/oversized/lost responses, persistence failure after server acceptance, retained known IDs, safe recheck without another POST, concurrent clients sharing one submission |

## Recovery policy

The durable `uploading` state is written before transmitting the FIT. A confirmed positive Strava upload ID is then saved before polling; an activity ID is saved before elevation verification. Known IDs are always reused, even after a failed request. Invalid/absent IDs, a lost submission response, or process death while `uploading` never authorize another file POST. Manual and automatic requests use the same rule; the former manual bypass has been removed. If no ID can be confirmed, the user must check Strava and may export the FIT for manual submission only after confirming the activity is absent. No claim of server-side idempotency is made for `external_id`.

These tests exposed and guard fixes for resubmission after uncertain responses or interrupted `uploading` state, races between separate client/store instances, unchecked OAuth scopes and malformed tokens, automatic replay of a token POST by `HttpURLConnection`, acceptance of invalid upload IDs/elevation values, ignored initial processing errors, and stale verified state after a failed recheck. The existing recording, acknowledgment, ascent filtering, sample retention, and FIT encoding logic are unchanged.

## What remains unverified

| Test type | What it can establish | What it cannot establish |
| --- | --- | --- |
| Loopback HTTP regressions | Client serialization, response handling, durable state transitions, local duplicate prevention and reported-elevation comparison | Live Strava OAuth consent, granted scopes, TLS/service behavior, upload acceptance, rate-limit policy, duplicate detection or Strava's chosen elevation calculation |
| FIT/core validation | Corrected synthetic session/lap ascent, retained sample data and independent Garmin SDK decoding | Real ride sensor accuracy, correct identification of every lift, physical watch capture/transfer reliability |
| Android APK/signature and emulator smoke checks | Compilation, install/startup and foreground-service behavior when the emulator is available | Android Keystore lifecycle on the user's phone, browser/Strava deep-link delivery, Garmin Connect pairing, physical Bluetooth transfer or background survival during a ride |

A physical Garmin watch, Android phone with Garmin Connect, and an explicitly authorized real Strava upload are still required for end-to-end verification. Disable ordinary Garmin-to-Strava sync first, use Only You visibility for the first real test, include a marked lift and a real climb, and compare the corrected FIT, retained recording, and Strava ascent. That field test is not part of this automated work. Build status must keep `hardware_tested: false` and `strava_upload_tested: false`.
